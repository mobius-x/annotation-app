## 1. Цели и принципы

- Лёгкое, быстрое, отзывчивое приложение для аннотирования текста.
- Три колонки: проводник (слева), текст (по центру), аннотации (справа). Слева внизу — навигатор по аннотациям.
- Всё настраивается файлами: темы, настройки, горячие клавиши — читаемый JSON.
- Исходные файлы пользователя не портятся: аннотации хранятся в отдельных файлах формата Annotator.
- Среда разработки портативная: ничего не ставится в систему, всё лежит в папке проекта.
- Linux — после v1. Код пишется без жёсткой привязки к Windows (пути через `path`, платформенные ветки изолированы).
- `[v1.1]` Данные пользователя важнее удобства: любая операция, которая может потерять текст или заметку (правка в режиме «Только аннотации», удаление диапазона, внешнее изменение файла), либо запрещена, либо обратима, либо требует подтверждения.
- `[v1.1]` Приложение работает с русским текстом и русской раскладкой как с основным сценарием: кодировка Windows-1251, горячие клавиши на кириллической раскладке, русская сортировка и склонения.
- `[v1.1]` Сетевых запросов нет вообще (включая скрытые: словари проверки орфографии, обновления, телеметрия).

### 2.4. `[v1.1]` Политика версий

- В `app\.npmrc`: `save-exact=true`. Версии Electron, Svelte, CodeMirror, chokidar, zod, electron-vite фиксируются точно.

## 3. Архитектура

### 3.1. Процессы

| Процесс | Задачи |
|---|---|
| Main (Node) | Окно, диалоги, доступ к файловой системе, наблюдение за файлами, чтение и запись настроек и состояния, флаги Chromium (сглаживание), кодировки, восстановление |
| Preload | Безопасный мост `window.api` (contextBridge), список разрешённых IPC-каналов |
| Renderer (Svelte) | Интерфейс, CodeMirror, состояние аннотаций, темы |

Безопасность: `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, строгая CSP, запрет `eval`, запрет открытия внешних URL внутри окна.

`[v1.1]` Уточнения:

- **Протокол и CSP.** Интерфейс загружается не по `file://`, а по собственному протоколу `app://` (`protocol.handle`), чтобы CSP можно было выдавать заголовком. Продакшен-CSP: `default-src 'self'; script-src 'self'; style-src 'self' 'nonce-<случайный на запуск>'; img-src 'self' data:; font-src 'self' data:; connect-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'`. В режиме разработки CSP шире (HMR Vite требует `'unsafe-inline'` для стилей и `ws:`); профили CSP хранятся отдельно.
- **Стили CodeMirror.** CodeMirror 6 вставляет свои стили элементами `<style>`; nonce передаётся через `EditorView.cspNonce.of(nonce)` (фасет существует в `@codemirror/view`). Nonce выдаётся preload-скриптом/страницей на каждый запуск.
- **Инлайновые стили.** Атрибут `style`, выставленный через `setAttribute`, может блокироваться CSP; поэтому в decorations и компонентах не использовать `attributes: { style }` и `style="..."`-строки. Допустимо: классы, CSSOM (`el.style.setProperty`, `CSSStyleSheet.insertRule`, `adoptedStyleSheets`). Персональные цвета аннотаций и типы реализуются классами, порождаемыми через CSSOM (см. 6.1). Проверить на спайке S1.
- **Разрешения.** По умолчанию Electron одобряет любые запросы разрешений. Включить `session.setPermissionRequestHandler((...)=>cb(false))` и `setPermissionCheckHandler(()=>false)`; приложению не нужны ни камера, ни уведомления, ни буфер обмена вне стандартных событий copy/paste.
- **Навигация.** `webContents.setWindowOpenHandler(() => ({ action: 'deny' }))`, перехват `will-navigate`. Ссылки из заметок открываются в браузере системы через IPC `shell.openExternal` только для схем `http`, `https`, `mailto`.
- **Preload в песочнице.** При `sandbox: true` preload должен быть единым бандлом в формате CommonJS без `require` локальных модулей; электрон-vite настраивается соответственно. Нужно подтвердить на спайке S1 (в документации Electron ESM-preload связан с отключённой песочницей).
- **Меню.** Нативное меню приложения отключено: `Menu.setApplicationMenu(null)`. Причины: стандартные роли меню перехватывают Ctrl+W, Ctrl+0 и Ctrl+Shift+I, а нажатие Alt на Windows передаёт фокус строке меню, что ломает Alt+Up/Alt+Down. Все команды доступны через панель команд, тулбар и горячие клавиши (раздел 12). DevTools — по F12 только в режиме разработки.
- **Контекстные меню.** В Electron стандартного контекстного меню у полей ввода нет: меню «Вырезать / Копировать / Вставить / Выделить всё» для редактора и textarea строится через `webContents.on('context-menu')` и `Menu.buildFromTemplate`.
- **Проверка орфографии отключена** (`spellcheck: false`): на Windows Electron скачивает словари Hunspell с CDN Google, что нарушает принцип «без сетевых запросов». Собственные локальные словари — после v1.

### 3.4. `[v1.1]` IPC и доступ к файловой системе

- Все каналы перечислены в одном файле контракта (`src/shared/ipc-contract.ts`): имя, схема запроса (`zod`), схема ответа. Preload экспортирует только эти каналы.
- Главный процесс проверяет вход каждого вызова схемой `zod` и источник вызова (`event.senderFrame.url` начинается с `app://`).
- Доступ к путям ограничен «разрешёнными корнями»: папки текущего workspace, файлы, выбранные пользователем через системные диалоги, `userData`. Запрос пути вне этого набора отклоняется.
- Группы каналов: `fs:*` (чтение, атомарная запись, список папки, создание, переименование, перенос, копирование, удаление в корзину), `watch:*` (подписка на события, приостановка), `settings:*`, `state:*`, `dialog:*`, `fonts:list`, `recovery:*`, `shell:openExternal`, `shell:showItemInFolder`, `app:relaunch`.
- Файловые операции возвращают структурированную ошибку (`code`: `EEXIST`, `EPERM`, `EBUSY`, `ENOENT`, `ENAMETOOLONG`, …) для сообщений на русском.
- Для сброса файлов из системного Проводника на окно имя пути получается в preload через `webUtils.getPathForFile(file)`: свойство `File.path` удалено в Electron 32.

### 3.5. `[v1.1]` Настройки и состояние

- `settings.json` — конфигурация пользователя. Приложение меняет его только по явному действию пользователя (диалог настроек). Если файл повреждён или не проходит `zod`, приложение запускается с настройками по умолчанию, показывает ошибку с номером строки и **не перезаписывает** файл (копия остаётся как есть).
- `state.json` в `userData` — состояние, которым управляет приложение: размеры и положение окна, ширины колонок, высота Outline, последний workspace, недавние файлы, раскладка вкладок без workspace. Пишется с задержкой 500 мс после изменения, атомарно.
- Правка `settings.json` вручную применяется на лету (наблюдение за файлом, проверка схемой, откат к предыдущему корректному состоянию при ошибке).
- Версионирование: поле `version`; при открытии файла старой версии выполняется миграция с копией `settings.json.bak`.

## 5. Проводник и workspace

### 5.1. Workspace

- Workspace — набор одной или нескольких корневых папок (как в VS Code).
- Команды: «Открыть папку», «Добавить папку в workspace», «Сохранить workspace как…», «Открыть workspace».
- Файл workspace: `*.annotator-workspace` (JSON):

```json
{
  "version": 1,
  "folders": [
    { "path": "../texts/book1", "name": "Книга 1" },
    { "path": "../texts/articles" }
  ],
  "settings": { "editor": { "fontSize": 17 }, "theme": "solarized-light" },
  "state": { "openTabs": ["../texts/book1/ch1.txt"], "activeTab": 0 }
}
```

- Без файла workspace последняя открытая папка запоминается в `state.json`.
- `[v1.1]` Пути в файле workspace хранятся **относительно папки файла workspace**, с разделителем `/`; абсолютный путь допускается, только если папка находится на другом диске. Так workspace переживает перенос проекта и работает на Linux.
- `[v1.1]` `settings` внутри workspace имеют ту же вложенную структуру, что и глобальные настройки (в v1.0 пример использовал плоский ключ `"editor.fontSize"`), и объединяются с глобальными глубоким слиянием. Переопределять в workspace можно только: `theme`, `editor.*`, `annotationsPanel.*`, `annotations.*`, `focusView.*`, `files.saveFormat`, `files.autosave*`. Параметры `rendering.*` (применяются при запуске до открытия workspace), `keybindings`, `ui.zoom` в workspace не переопределяются.
- `[v1.1]` Если папка workspace недоступна (диск отключён) — в дереве корень с пометкой «недоступна» и кнопкой «Повторить», остальные корни работают.

### 5.2. Дерево

- Иерархия с отступами и стрелками раскрытия, иконки папок и файлов, сортировка: папки сверху, затем файлы по имени. `[v1.1]` Естественная сортировка без учёта регистра реализуется как `new Intl.Collator('ru', { numeric: true, sensitivity: 'base' })` (числа сравниваются как числа, «ё» и «е» различаются по правилам локали).
- Отображаемые файлы: `.txt`, `.md`, `.annot.json`, `.annot.md`. Остальные скрыты (опция «показывать все файлы»). `[v1.1]` Не показываются и не просматриваются папки `.git`, `node_modules`, служебные файлы приложения (`*.tmp`, временные файлы записи с префиксом `.~`, `*.bak`). Символические ссылки и junction не разворачиваются (защита от циклов).
- Файлы, у которых есть аннотированная версия, помечаются значком. `[v1.1]` Файл `X.annot.*`, рядом с которым лежит исходный `X.*`, **скрывается из дерева** (опция `explorer.showAnnotFiles`, по умолчанию `false`); открытие `X.txt` открывает аннотированную версию (см. 11.5). `.annot.*` без исходного файла показывается как обычный файл. Если рядом лежат и `X.annot.json`, и `X.annot.md`, у исходного файла значок предупреждения «конфликт форматов».
- Контекстное меню: Новый файл, Новая папка, Переименовать (F2), Удалить (в корзину), Показать в Проводнике Windows, Копировать путь.
- Создание файла: в дереве появляется поле ввода имени на нужном уровне. Если расширение не указано, добавляется `.txt`.
- `[v1.1]` Проверка имён по правилам Windows: запрещены символы `< > : " / \ | ? *`, управляющие символы, имена `CON`, `PRN`, `AUX`, `NUL`, `COM1–9`, `LPT1–9`, имя не может заканчиваться точкой или пробелом, длина пути — не более 259 символов. Ошибка показывается рядом с полем.
- `[v1.1]` Переименование и удаление затрагивают связанные файлы аннотаций: при `X.txt → Y.txt` переименовываются `X.annot.json/.md → Y.annot.json/.md` и обновляется `document.source`; при удалении `X.txt` приложение спрашивает «Удалить также файл аннотаций?» (по умолчанию — нет, файл остаётся и становится самостоятельным документом). Удаление выполняется через `shell.trashItem` и **не входит** в стек отмены проводника (API корзины не умеет восстанавливать элементы).
- Клавиатура: стрелки, Enter (открыть), Left/Right (свернуть, развернуть), F2, Delete. `[v1.1]` ARIA-разметка дерева (`role="tree"`, `treeitem`, `aria-expanded`, `aria-selected`).
- Наблюдение за диском через `chokidar`. `[v1.1]` Правила наблюдения:
  - «Задержка 100 мс» — это окно группировки событий (debounce), а не `awaitWriteFinish`; для файлов, которые приложение читает, дополнительно используется `awaitWriteFinish` с `stabilityThreshold` 200 мс, чтобы не читать наполовину записанный файл.
  - Наблюдаются только раскрытые папки и открытые файлы (а не весь workspace рекурсивно); `ignoreInitial: true`; `ignored` — по правилам выше.
  - События, вызванные собственной записью приложения (временный файл и `rename` при автосохранении), подавляются: приложение запоминает путь и SHA-256 последней записи и игнорирует событие с тем же хэшем в течение 2 секунд. Без этого каждое автосохранение вызвало бы запрос «Перезагрузить / Оставить».
  - На Windows наблюдение за папкой может блокировать её переименование и удаление (`EPERM`/`EBUSY`): перед операцией над папкой её наблюдатель снимается и после завершения восстанавливается. Проверить на спайке S6.
  - Внешние изменения отражаются в дереве. Открытый файл, изменённый снаружи, вызывает запрос «Перезагрузить / Оставить»; при несохранённых локальных правках формулировка — «Файл изменён на диске. Перезагрузить (локальные правки будут потеряны) / Оставить мои правки / Сравнить».

### 5.3. Перетаскивание (drag and drop)

Поддерживается перенос файлов и папок. Зона сброса определяется по вертикальной позиции курсора внутри строки:

| Положение курсора | Цель | Индикатор |
|---|---|---|
| Центральная часть строки папки (около 50% высоты) | Внутрь папки | Подсвечивается вся строка папки |
| Верхняя или нижняя четверть строки | В родительскую папку этого элемента (на один уровень с ним) | `[v1.1]` Подсвечивается блок родительской папки (рамка вокруг её содержимого, как в VS Code); для верхнего уровня — рамка вокруг всего дерева |
| Центральная часть строки файла | В родительскую папку этого файла | Подсвечивается блок родительской папки |
| Пустая область под деревом | В корень workspace | Рамка вокруг всего дерева (при нескольких корнях — вокруг ближайшего корня; корень определяется по ближайшему сверху) |

`[v1.1]` Индикатор «горизонтальная линия между строками» из v1.0 заменён подсветкой целевой папки: порядок элементов внутри папки не сохраняется (он определяется сортировкой), и линия обещала бы позицию, которой не будет. Если вы предпочитаете линию — её можно вернуть, зона сброса от этого не меняется.

Правила:
- Папка раскрывается автоматически, если курсор над ней дольше 600 мс.
- Запрещено перенести папку внутрь самой себя или потомка. Курсор показывает запрет. `[v1.1]` Запрещён перенос в текущую родительскую папку (операция без эффекта: курсор «нельзя»).
- Конфликт имён: диалог «Заменить / Оставить оба (добавить суффикс ` (2)`) / Отмена». `[v1.1]` Для нескольких элементов — флажок «Применить ко всем».
- Ctrl при сбросе — копирование вместо переноса.
- Можно переносить несколько выделенных элементов (Ctrl и Shift при выборе).
- Перенос внутри одного тома — `fs.rename`. Между томами (ошибка `EXDEV`) — копирование и удаление. `[v1.1]` Папки копируются рекурсивно с проверкой результата перед удалением источника; при ошибке на середине операции источник остаётся нетронутым, а копия удаляется.
- При переносе вместе с файлом переносятся связанные файлы аннотаций (`name.annot.json` / `name.annot.md`), и ссылки `source` в них обновляются. `[v1.1]` То же — при копировании (Ctrl) и при переименовании (см. 5.2). Если перенос пары файлов прошёл наполовину — откат первого.
- Ctrl+Z в проводнике отменяет последнюю файловую операцию (стек в памяти, 20 действий). `[v1.1]` Пакетная операция над несколькими элементами — одно действие стека. Отменяются: перенос, копирование, переименование, создание. **Не отменяется** удаление в корзину (см. 5.2). Ctrl+Z действует на проводник, только если фокус в нём.
- Порядок элементов внутри папки не сохраняется вручную: он всегда определяется сортировкой. Поэтому «на один уровень с папками» означает выбор родительской папки.
- `[v1.1]` Сброс файлов из системного Проводника Windows: на область редактора или вкладок — открыть файл; на дерево — после v1 (копирование в папку).

## 6. Редактор (центральная колонка)

- Движок: CodeMirror 6. Режим по умолчанию — редактируемый текст с переносом строк. Переключатель «только чтение» в тулбаре. `[v1.1]` «Только чтение» запрещает **правки текста**, но не создание и редактирование аннотаций (аннотации не меняют текст; в этом режиме привязки наиболее устойчивы). Режим хранится на вкладку; значение `editor.readOnly` — только начальное для новых вкладок.
- Для `.md` включена подсветка синтаксиса Markdown (`@codemirror/lang-markdown`), для `.txt` — без подсветки.
- Нумерация строк — опция (по умолчанию выключена).
- Шрифт, размер, межстрочный интервал берутся из настроек (раздел 9).
- `[v1.1]` Поиск по документу: Ctrl+F (`@codemirror/search`), замена — только в режиме редактирования.
- `[v1.1]` Набор команд CodeMirror собирается явно, а не берётся целиком из `defaultKeymap`: из него исключены привязки, конфликтующие с приложением (`Alt-ArrowUp`/`Alt-ArrowDown` — перемещение строки, `Mod-Enter` и т. п.). Навигация по аннотациям (Alt+Up/Alt+Down) регистрируется с повышенным приоритетом (`Prec.high`).
- `[v1.1]` Сочетания клавиш сопоставляются по **физической клавише** (`event.code`: `KeyS`, `KeyA`, …), а не по символу (`event.key`), иначе на русской раскладке Ctrl+S, Ctrl+Shift+A и остальные не работают. Для самого CodeMirror используется его keymap-механизм, который учитывает не-латинские раскладки; для остального — собственный диспетчер (раздел 12). Тестировать на русской и английской раскладках.
- `[v1.1]` Проверка орфографии отключена (см. 3.1).

### 6.0. `[v1.1]` Кодировки, переводы строк, BOM

- Чтение файла: (1) BOM `EF BB BF` → UTF-8, `FF FE`/`FE FF` → UTF-16; (2) строгое декодирование `TextDecoder('utf-8', { fatal: true })`; (3) при ошибке — определение через `chardet`; если уверенность низкая, а текст содержит байты 0x80–0xFF, предлагается Windows-1251 с диалогом «Выбрать кодировку»; (4) всегда доступна команда «Переоткрыть с кодировкой…» (статус-бар).
- Внутри редактора перевод строки — `\n`. Нормализуются `\r\n` и одиночный `\r`. Исходный стиль запоминается; при смешанных окончаниях запоминается преобладающий, а пользователь получает уведомление «Файл содержал смешанные переводы строк». Наличие или отсутствие завершающего перевода строки в конце файла сохраняется.
- Запись **обычного** файла (без аннотированной версии): в исходной кодировке (Windows-1251 через `iconv-lite`), с исходными BOM и стилем перевода строки. Символы, которых нет в кодировке, → запрос «Сохранить в UTF-8».
- Запись `.annot.*` — всегда UTF-8 без BOM (раздел 11). Поэтому после появления аннотаций проблемы кодировки исходного файла перестают влиять на привязки.
- Смещения аннотаций считаются в единицах UTF-16 (как в CodeMirror) от начала нормализованного текста.

### 6.1. Подсветка аннотированного текста

- Реализация: mark-декорации CodeMirror 6 — они оборачивают диапазон текста элементом с классом.
- `[v1.1]` Диапазоны и записи аннотаций хранятся в отдельном `StateField` (`annotationField`: `id → {range, ...}`), а набор mark-декораций строится из него. Нельзя считать декорации единственным хранилищем: при сворачивании диапазона до нуля (удалён весь фрагмент) mark-диапазон может быть отброшен при маппинге, а запись об аннотации должна остаться (см. 6.4). При правке текста смещения пересчитываются автоматически через `changes.mapPos`.
- Цвет подсветки: `color-mix(in srgb, var(--annot-color) calc(var(--annot-alpha) * 100%), transparent)`.
- `[v1.1]` Каждому типу (и каждому персональному цвету) соответствует CSS-класс (`.annot-t-question`, `.annot-c-<hash>`); значения `--annot-color` задаются в таблице стилей через CSSOM, а не через атрибут `style` (см. 3.1). Подложка — фон на самом `mark`-элементе (не накладываемый слой), чтобы не ломать сглаживание ClearType (9.3).
- Параметры в настройках: `annotations.highlightAlpha` (0.05–0.6, по умолчанию 0.18), цвет по умолчанию, цвет для каждого типа.
- `[v1.1]` **Приоритет цвета аннотации**: личный `annotation.color` → `annotations.types[i].color` из `settings.json` (если задан, не `null`) → `annot.<id типа>` из темы → `annotations.highlightColor` (если задан и `colorByType = false`) → `annot.default` из темы. Значения по умолчанию в `settings.json` для типов — `color: null`, чтобы цвета типов определяла тема (иначе пользовательские цвета типов в настройках всегда перекрывали бы цвета темы и темы не меняли бы цвет подсветки).
- Активная аннотация (выбрана справа или курсор внутри неё) подсвечивается сильнее и получает нижнюю границу 2 px. `[v1.1]` Формула: `activeAlpha = max(alpha, min(alpha + 0.12, 0.35))` (в v1.0: `alpha × 1.8`, максимум 0.7). При значении 0.7 контраст основного текста на подсветке падает ниже 2:1 почти во всех тёмных темах (см. Приложение B); основной сигнал активности — граница.
- Вложенные аннотации: более короткая рисуется поверх (z-порядок по длине). Пересекающиеся (не вложенные) допускаются в JSON.
- Наведение мыши на подсвеченный фрагмент подсвечивает карточку справа, клик выбирает её. `[v1.1]` Если под курсором несколько вложенных аннотаций, выбирается самая короткая; повторный клик на том же месте выбирает следующую (по возрастанию длины).
- `[v1.1]` Анимация «мигание» отключается при `prefers-reduced-motion`.

### 6.2. Создание аннотации

1. Пользователь выделяет текст мышью или клавиатурой. Выделение не пустое — рядом с концом выделения появляется плавающая иконка. Реализация: подсказка (`showTooltip`) CodeMirror, привязанная к выделению. Пример из документации обрабатывает только пустые курсоры, поэтому нужен фильтр на непустые диапазоны. `[v1.1]` Не показывается, если выделение состоит только из пробелов и переводов строк, и во время набора через IME (композиция).
2. Иконка не показывается, пока зажата кнопка мыши (появляется после `mouseup`), и пропадает при пустом выделении, прокрутке, нажатии Esc. `[v1.1]` У иконки на `mousedown` вызывается `preventDefault()`, чтобы клик не сбрасывал выделение до создания аннотации.
3. Клик по иконке (или Ctrl+Shift+A) создаёт аннотацию:
   - в редактор добавляется диапазон с подсветкой;
   - справа вставляется новая карточка в нужную позицию списка;
   - правая колонка прокручивается к ней, фокус переходит в многострочное поле ввода текста (`textarea.focus()`).
4. В поле ввода: Ctrl+Enter — подтвердить, Esc — отменить (если поле пусто, аннотация удаляется), Tab — переход к выбору типа.
5. Новая пустая аннотация не записывается на диск, пока не введён текст или пока пользователь явно не подтвердил её. `[v1.1]` Для обычного файла без аннотированной версии это означает: файл `.annot.*` создаётся при первой **подтверждённой** аннотации (см. 11.5).
6. Выделение, которое полностью совпадает с существующей аннотацией, не создаёт новую, а открывает существующую для редактирования. `[v1.1]` Если совпадающих аннотаций несколько — открывается первая по порядку создания; остальные доступны кликом по подсветке (см. 6.1).
7. `[v1.1]` Выделение, частично пересекающееся с существующей аннотацией, допускается (пересекающиеся диапазоны разрешены).

### 6.3. Режим «Только аннотации» (Focus view)

Кнопка в тулбаре (и клавиша F9) переключает режим. В нём виден только аннотированный текст:

- Показываются только фрагменты, у которых есть аннотация. Неаннотированный текст скрыт.
- Между фрагментами — две пустые строки.
- Фрагменты идут в порядке появления в документе.
- Если фрагменты пересекаются или соприкасаются, они объединяются в один блок (объединение диапазонов), чтобы не дублировать текст.
- Реализация: блочные replace-декорации (`Decoration.replace({ block: true })`) над промежутками между аннотациями; каждая замена рисует пустой блок высотой в две строки. Это сохраняет единую модель смещений: выделение, подсветка и создание аннотаций продолжают работать. `[v1.1]` Ограничения реализации:
  - Блочные виджеты и декорации, замещающие переводы строк, должны поставляться **напрямую** (из `StateField` через `EditorView.decorations.from(field)`), а не функцией и не из `ViewPlugin`: документация `@codemirror/view` разрешает прямым наборам влиять на вертикальную раскладку, а функциональным — нет.
  - Обязательно проверить на спайке S2 случай, когда промежуток начинается или заканчивается **внутри строки** (аннотированное слово в середине предложения — самый частый случай): в документации не сказано, что блочная замена обязана покрывать строки целиком. Запасной вариант A: промежутки внутри строки скрываются встроенной (inline) заменой, а блочная замена применяется только к промежуткам, покрывающим целые строки. Запасной вариант B: режим рисуется вторым, только читаемым `EditorView` над производным документом (склеенные фрагменты) с таблицей соответствия смещений.
- **Безопасность данных `[v1.1]`:** в этом режиме текст **нельзя править**: включается `EditorState.readOnly`, плюс `transactionFilter` отклоняет любые транзакции, меняющие документ (иначе выделение через скрытую область и Delete удалили бы невидимый текст). Курсор пропускает скрытые области через `atomicRanges`; копирование выделения через скрытые области отфильтровывается через `EditorView.clipboardOutputFilter`, в буфер попадает только видимый текст. Создание и правка аннотаций в режиме разрешены.
- Опция `focusView.contextChars` (по умолчанию 0): сколько символов контекста оставлять вокруг фрагмента.
- Опция `focusView.separator` (по умолчанию `"blank2"`): `"blank2"` — две пустые строки; `"rule"` — линия-разделитель.
- Клик по фрагменту выбирает карточку справа. Двойной клик выходит из режима и ставит курсор в это место полного текста.
- Состояние режима хранится для каждой вкладки отдельно.
- `[v1.1]` Аннотации в состоянии `orphan` (без привязки) в режиме не отображаются; в правой панели они остаются в своей группе.

### 6.4. `[v1.1]` Правка текста и устойчивость привязок

- **Границы.** Диапазон аннотации не «липкий»: текст, набранный вплотную к началу или концу фрагмента, в аннотацию не входит (`inclusiveStart: false`, `inclusiveEnd: false`). Вставка внутрь диапазона расширяет его, удаление части — сжимает.
- **Схлопывание.** Если весь аннотированный фрагмент удалён или заменён целиком (диапазон стал пустым), аннотация **не удаляется**: она переходит в состояние `orphan`, сохраняя заметку, теги и последнюю известную цитату, и показывается в группе «Без привязки» (раздел 7) с возможностью «Привязать к выделению» или «Удалить». Правило: заметка пользователя не пропадает молча.
- **Единая история.** Создание, удаление и изменение типа/цвета/флага «решено» аннотаций проводятся как `StateEffect` со своими `invertedEffects` в той же истории (`@codemirror/commands`), что и правки текста. Ctrl+Z, вызванный из редактора, отменяет текст и такие действия вместе. Текст заметки редактируется в `textarea` с её нативным undo; Ctrl+Z действует на ту панель, где находится фокус. Подтверждение заметки (Ctrl+Enter) — одна запись истории.
- **Две модели состояния.** Источник истины по позициям — `annotationField` (CodeMirror); по содержимому (заметка, теги, тип) — модуль `annotations.svelte.ts`, ключ — `id`. Подписка на изменение позиций в UI троттлится (один раз за кадр) и пересчитывает только изменившееся.
- **При сохранении** для каждой привязанной аннотации заново вычисляются `quote.exact`, `prefix`, `suffix` и `range` по текущим позициям; `textSha256` пересчитывается.
- **Внешние изменения файла** обрабатываются только восстановлением по цитате (11.2) и показом отчёта.
- **Контекстное меню редактора:** Вырезать, Копировать, Вставить, Выделить всё, Создать аннотацию (если есть выделение).

## 7. Панель аннотаций (правая колонка)

Карточка аннотации содержит:
- цветную полоску и значок типа;
- цитату (первые 120 символов выделенного текста, мелким шрифтом, сворачиваемую);
- текст заметки (поддерживается простой Markdown: жирный, курсив, код, списки, ссылки);
- теги (`#тег`), дату изменения, флаг «решено».

Поведение:
- Порядок — по позиции в тексте (по возрастанию `start`). Опциональная сортировка: по дате создания.
- Клик по карточке прокручивает текст к фрагменту (центрирование), фрагмент мигает.
- Двойной клик — редактирование. Кнопки: тип, цвет, удалить (с отменой Ctrl+Z), «решено».
- Фильтр над списком: поиск по тексту, по тегам, по типу, «скрыть решённые».
- Прокрутка текста синхронизирует список: карточки видимых аннотаций подсвечиваются, список автоматически прокручивается (опция «связать прокрутку», по умолчанию включена).
- Типы по умолчанию: `comment`, `note`, `question`, `idea`, `todo`, `important`. Список типов редактируется в настройках (id, название, цвет).

`[v1.1]` Дополнения:

- **Отрисовка заметок.** Markdown → HTML через `markdown-it` с `html: false`, результат очищается `DOMPurify`. Ссылки не открываются в окне: клик отправляет URL в `shell:openExternal` (схемы `http`, `https`, `mailto`). Ничего из текста заметки не вставляется в DOM без очистки.
- **Виртуализация.** При 5 000 аннотаций панель использует виртуальный список (`VirtualList.svelte`) с измеряемой высотой карточек; в DOM — только видимые карточки и запас. Прокрутка к карточке и «связать прокрутку» работают по индексам, а не по элементам. Видимые аннотации в тексте определяются по `view.visibleRanges` бинарным поиском по отсортированным `start`. Прокрутка списка, вызванная кликом или синхронизацией, на короткое время (≈150 мс) не запускает обратную синхронизацию (защита от петли).
- **Группа «Без привязки» (orphan).** Аннотации, привязку которых не удалось восстановить (11.2) или диапазон которых схлопнулся (6.4), показываются в отдельной сворачиваемой группе вверху панели. Действия: «Привязать к выделению» (берёт текущее выделение в тексте), «Найти заново» (повторный поиск по цитате), «Удалить». Цитата и заметка видны.
- **Теги.** Вводятся как `#тег` или в отдельном поле; хранятся без `#`; пробелы заменяются на `_`; регистр сохраняется, сравнение при фильтре — без учёта регистра; дубликаты убираются.
- **Клавиатура.** Карточка фокусируется Tab/стрелками (`role="listbox"` с `option`), Enter — редактировать, Delete — удалить (отмена Ctrl+Z), Space — «решено».
- Тип отображается значком и подписью, а не только цветом (доступность при нарушении цветового зрения).

## 8. Outline (быстрая навигация, слева внизу)

- Плоский список всех аннотаций текущего документа по порядку в тексте.
- Строка: цветная точка типа · первые 50 символов цитаты · начало заметки (приглушённым цветом) · номер строки.
- Клик или Enter — переход к аннотации (как в Outline VS Code). Стрелки вверх/вниз перемещают выбор, Alt+Up / Alt+Down — глобальные «предыдущая / следующая аннотация» (работают из любой панели).
- Текущая аннотация (в которой стоит курсор) подсвечивается в списке автоматически («следовать за курсором»).
- Фильтр: текстовое поле, кнопки типов, переключатель «группировать по типу».
- Сворачиваемый заголовок, запоминание высоты блока.
- `[v1.1]` Список виртуализируется так же, как панель аннотаций. «Номер строки» — номер **логической** строки документа (не визуальной строки с переносом). Аннотации без привязки показываются в конце списка с пометкой «без привязки» и недоступны для перехода.
- `[v1.1]` Alt+Up/Alt+Down реализованы приложением, а не нативным меню (меню отключено, см. 3.1) и перекрывают стандартную привязку CodeMirror «переместить строку» (см. раздел 6). Если текущего выбора нет, «следующая» — первая аннотация после курсора, «предыдущая» — последняя перед курсором; на границе документа — циклический переход с коротким уведомлением.

### 9.2. Шрифты

- Раздельные настройки для интерфейса, основного текста и аннотаций: семейство, размер (8–48 px), для редактора ещё толщина и интерполяция строк.
- Список шрифтов: основной способ — `queryLocalFonts()` (Local Font Access API Chromium). `[v1.1]` По данным разбора разрешений Electron (Doyensec, 2022), для этого API запрос разрешения в главный процесс не доходит и `setPermissionRequestHandler` его не фильтрует; на выбранной версии Electron это нужно перепроверить на спайке S4, но обработчик разрешений из 3.1 запрещает остальные, а этот вызов должен сработать по жесту пользователя (клик по выпадающему списку). Запасной вариант: чтение списка из реестра `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Fonts` и `HKCU\...\Fonts` через `reg query` (дочерний процесс без нативных модулей) + ручной ввод имени + встроенный список (Segoe UI, Calibri, Cambria, Georgia, Consolas, Cascadia Mono, Arial, Times New Roman, Verdana, Tahoma).
- Строка `fontFamily` принимает цепочку запасных шрифтов (CSS-синтаксис).
- Предпросмотр на тестовом тексте прямо в окне настроек. `[v1.1]` Тестовый текст содержит кириллицу, латиницу, цифры и знаки препинания, чтобы сразу было видно шрифты без кириллицы (браузер подставит запасной шрифт, и вид абзаца изменится).
- Ctrl+колесо мыши меняет размер основного текста, Ctrl+0 сбрасывает. `[v1.1]` Значение сохраняется в `settings.json` с задержкой 500 мс после последнего шага, чтобы не переписывать файл на каждый щелчок колеса.

### 9.3. Сглаживание текста (Windows)

Параметр `rendering.smoothing`. Применяется при запуске (требуется перезапуск). Флаги Chromium выставляются в `src/main/index.ts` до `app.whenReady()` через `app.commandLine.appendSwitch(...)`.

| Значение | Поведение | Реализация |
|---|---|---|
| `system` (по умолчанию) | Как настроено в Windows. Если в системе включён ClearType, Chromium использует субпиксельное сглаживание, иначе серое | Ничего не добавляется |
| `grayscale` | Сглаживание оттенками серого, без цветной окантовки. Подходит для OLED и нестандартных субпикселей | `appendSwitch('disable-lcd-text')` — флаг Chromium; ранее использовался как обходной путь в VS Code. Эффект зависит от монитора и настроек ClearType (проверить на целевой машине, спайк S5) |

`[v1.1]` Значение `cleartype` из v1.0 удалено: в v1.0 оно описывалось как «включается только если ClearType включён в Windows», то есть поведение совпадало с `system`, а флагов не добавлялось. Гарантия непрозрачных фонов у контейнеров текста (без `opacity`, `transform`, `will-change`, `backdrop-filter` на предках текста, иначе Chromium переходит на серое сглаживание) теперь действует **всегда**, при любом значении. Если спайк S5 покажет, что флаг `enable-lcd-text` реально включает LCD-сглаживание там, где `system` его не даёт, значение `cleartype` возвращается с этим флагом (не подтверждено, требует проверки на машине).

- Режим «без сглаживания» (aliased) в v1 не поддерживается: в приложениях на Chromium отключить сглаживание шрифтов на Windows нельзя, единственный путь — отключить ClearType и сглаживание в самой Windows. В интерфейсе настроек показывается подсказка об этом и ссылка на «Настройку текста ClearType».
- Дополнительная опция `rendering.subpixelPositioning` (`default` / `on` / `off`) — экспериментальная. Флаг `--disable-font-subpixel-positioning` в Chromium ведёт себя неочевидно, и на практике его эффект может быть обратным названию. Опция включается в v1 только после ручной проверки на целевой машине; до этого скрыта под флагом `experimental`.
- Режим `system` зависит от настроек Windows (Параметры → Персонализация → Шрифты → «Настройка ClearType»). `[v1.1]` Текущее состояние читается из реестра `HKCU\Control Panel\Desktop`: `FontSmoothing` (включено ли сглаживание) и `FontSmoothingType` (1 — стандартное, 2 — ClearType), через `reg query`; если прочитать не удалось, значение не показывается.
- `[v1.1]` Окно создаётся с непрозрачным `backgroundColor`, не используется `transparent: true` (прозрачное окно отключает LCD-сглаживание).
- CSS-свойство `-webkit-font-smoothing` на Windows не используется.
- В окне настроек рядом с выбором режима показывается тестовый абзац и текущее значение, прочитанное из системы (по возможности).
- Для сравнения режимов используется кнопка «Перезапустить и применить» (`app:relaunch`).

## 11. Формат хранения аннотированных документов

### 11.1. Общая модель

- Исходный файл (`ch1.txt`) никогда не изменяется без явной правки пользователя.
- Аннотированный документ — отдельный файл рядом с исходным: `ch1.annot.json` или `ch1.annot.md`. Он самодостаточен: содержит полный текст и все аннотации.
- Формат выбирается в настройках (`files.saveFormat`) и переопределяется для документа командой «Сохранить как…». Для документа одновременно существует только один формат; при смене формата старый файл заменяется (с подтверждением).
- Если открыт обычный файл без аннотированной версии, при первой аннотации создаётся файл `.annot.*`, а в нём копия текста. Внутри приложения редактируется именно текст из `.annot.*`.
- Если открыт сам `.annot.*`, редактируется он напрямую.
- Автосохранение, запись, резервные копии и восстановление — в 11.6.
- Кодировка — UTF-8 без BOM. Перевод строки записывается как в `document.eol`.
- Идентификаторы аннотаций: `a` + короткий случайный base36 (например, `a7k2m9`, 6 знаков), уникальны в пределах документа (при коллизии генерируется заново). Нумерация отдельным полем `order` не нужна: порядок определяется позицией.

### 11.2. Формат JSON (`*.annot.json`)

```json
{
  "format": "annotator-document",
  "version": 1,
  "document": {
    "title": "Глава 1",
    "source": "ch1.txt",
    "eol": "lf",
    "language": "plain",
    "textSha256": "9f2c…",
    "created": "2026-10-20T00:10:00Z",
    "modified": "2026-10-20T01:42:13Z"
  },
  "text": "Полный текст документа…",
  "annotations": [
    {
      "id": "a7k2m9",
      "type": "question",
      "range": { "start": 120, "end": 145 },
      "quote": {
        "exact": "фрагмент текста",
        "prefix": "30 символов до ",
        "suffix": " 30 символов после"
      },
      "body": "Заметка в формате Markdown.\nМожно несколько строк.",
      "tags": ["сюжет", "уточнить"],
      "color": null,
      "resolved": false,
      "created": "2026-10-20T00:12:41Z",
      "modified": "2026-10-20T00:12:41Z"
    }
  ],
  "extra": {}
}
```

Правила:
- `range.start/end` — смещения UTF-16 в `text` (после нормализации `\n`), `end` не включается. `[v1.1]` Инвариант: `0 ≤ start < end ≤ text.length` (пустые диапазоны недопустимы).
- `quote` — точная цитата и контекст (по 30 символов) по модели `TextQuoteSelector` из стандарта W3C Web Annotation: контекст `prefix` и `suffix` отличает повторяющиеся фрагменты. Используется для восстановления привязки, если `range` не совпал с текстом. `[v1.1]` Пересчитывается при каждой записи (6.4).
- Восстановление при загрузке: (1) если `text.slice(start, end) === exact`, всё в порядке; (2) иначе поиск `prefix+exact+suffix`; (3) иначе поиск `exact` ближайшего к `start` (при равном расстоянии — первое вхождение после `start`); (4) иначе аннотация помечается «потерявшей привязку» (`orphan`) и показывается в отдельной группе справа. `[v1.1]` После восстановления по шагам 2–3 приложение показывает отчёт «N аннотаций сдвинуты, M потеряли привязку».
- `[v1.1]` **Аннотация без привязки** хранится с `"range": null` и сохранённой `quote` (последней известной). При следующей загрузке приложение пробует найти её заново по шагам 2–3 и, если находит, возвращает привязку.
- `color: null` — цвет берётся у типа; строка `#rrggbb` — личный цвет аннотации (приоритет — 6.1).
- Неизвестные поля сохраняются при перезаписи (`extra` и поля на уровне аннотаций и документа): схема `zod` описывается с `.passthrough()` на всех уровнях.
- Валидация схемой (`zod`). Версия файла выше поддерживаемой — открытие только для чтения с предупреждением. `[v1.1]` Некорректный файл не открывается «частично»: показывается ошибка с путём к полю; пользователю предлагается открыть `.bak` или сам файл как текст.
- Аннотации в файле упорядочены по `range.start` (при равенстве — по `range.end` по убыванию, затем по `id`); аннотации без привязки — в конце.
- Допускаются вложенные и пересекающиеся диапазоны.
- `[v1.1]` `document.textSha256` — SHA-256 (hex) от UTF-8-байтов нормализованного текста (`\n`), пересчитывается при каждой записи. `document.language`: `"plain"` или `"markdown"`. `document.title` по умолчанию — имя файла без расширения. `document.source` — имя исходного файла относительно папки `.annot.*` (информационное поле, см. 11.5). Все даты — UTC ISO 8601.

### 11.3. Формат Markdown (`*.annot.md`)

Цель: файл читается и красиво выглядит в любом Markdown-просмотрщике (включая Obsidian), но полностью восстанавливается приложением.

Принципы:
- Текст документа записывается без изменений (за исключением экранирования зарезервированных последовательностей, ниже), а аннотированные фрагменты обрамляются маркерами выделения `==…==`, сразу за которыми стоит сноска `[^id]`.
- Заметка — это определение сноски `[^id]: …` в конце файла.
- Машинные данные (тип, цвет, теги, даты, «решено») — в одной строке комментария на сноску; метаданные документа и хэш текста — в YAML front matter.

Структура:

```markdown
---
annotator: 1
title: Глава 1
source: ch1.txt
eol: lf
language: plain
text_sha256: 9f2c…
created: 2026-10-20T00:10:00Z
modified: 2026-10-20T01:42:13Z
---

Обычный текст документа, где ==аннотированный фрагмент==[^a7k2m9] выделен,
а ==другой фрагмент с ==вложенным==[^b3x1q4] внутри==[^c9d8e7] тоже.

<!-- annotator:notes -->

[^a7k2m9]: <!--{"type":"question","tags":["сюжет","уточнить"],"resolved":false,"created":"2026-10-20T00:12:41Z","modified":"2026-10-20T00:12:41Z"}-->
    Заметка в формате Markdown.
    Можно несколько строк.

[^b3x1q4]: <!--{"type":"note","created":"2026-10-20T00:20:00Z","modified":"2026-10-20T00:20:00Z"}-->
    Вторая заметка.

[^c9d8e7]: <!--{"type":"idea","color":"#2ecc71","created":"2026-10-20T00:25:00Z","modified":"2026-10-20T00:25:00Z"}-->
    Третья заметка.
```

`[v1.1]` Метаданные сноски — **один JSON-объект** в комментарии вместо `key=value` из v1.0: теги с пробелами, запятыми и кириллицей, кавычки и неизвестные поля иначе потребовали бы собственного парсера с правилами экранирования. Символ `>` внутри JSON записывается как `\u003e`, чтобы текст не мог закрыть комментарий. Если вам важнее читаемость `key=value` — формат можно вернуть, но парсер и тесты придётся описать отдельно.

**Раскладка файла (нормативно).** Файл = front matter (`---\n…---\n`) + `\n` + ТЕКСТ + `\n\n<!-- annotator:notes -->\n` + область заметок. Переводы строк в файле — как в `document.eol`. ТЕКСТ — нормализованный текст документа с маркерами и экранированием; перед разделителем всегда записываются ровно два `\n`, поэтому любые пробелы и переводы строк в конце текста сохраняются при чтении (читатель отрезает ровно эти два `\n`; при ручной правке допускается один). Область заметок — после строки-разделителя.

**Экранирование (нормативно).** Правила v1.0 (`\==`, `\[^`, `\<!--`) не однозначны в двух случаях: (а) аннотация начинается сразу после обратной косой черты (текст `a\`, затем маркер): запись `a\==b…` читается как экранированный литерал `==`, и маркер открытия теряется; (б) литеральный `=` вплотную к маркеру (`x=` + маркер → `x===`): при чтении маркер находится на 2 символа левее. Новые правила:

- Зарезервированные последовательности: маркер открытия `==`, маркер закрытия `==[^id]`, текстовый литерал `[^`, строка `<!--`.
- **Запись.** Для каждого символа исходного текста `T` (маркеры вставляются по позициям диапазонов):
  - `=` → `\=`, если слева или справа в `T` стоит другой `=`, либо рядом (вплотную) вставляется маркер;
  - `[` → `\[`, если следующий символ в `T` — `^`;
  - `<` → `\<`, если далее в `T` идёт `!--`;
  - `\` → `\\`, если следующий символ в `T` — один из `\`, `=`, `[`, `<`, либо сразу после него вставляется маркер;
  - остальные символы без изменений (общие Markdown-экранирования вроде `\*` не затрагиваются).
- **Чтение** (слева направо): `\` + один из `\`, `=`, `[`, `<` → выдать второй символ как литерал; `==[^id]` (где `id` — `[A-Za-z0-9_~-]+`, затем `]`) → маркер закрытия; иной `==` → маркер открытия; иной `\` → литерал `\`.
- Инвариант: `unescape(escape(T)) === T` для любого текста и любых позиций маркеров. Проверяется property-based тестом (`fast-check`) на алфавите `= [ ^ < ! - \ ] a \n` с маркерами в случайных позициях.
- Результат безопасен для Obsidian: `\=` отображается как `=`.

**Парсинг диапазонов.** Лексер (выше) формирует стек открытых маркеров. Маркер закрытия `==[^id]` закрывает **ближайший незакрытый** маркер открытия слева (стек). Поэтому поддерживается вложенность, в том числе совпадающие начала и концы. Позиции `start/end` вычисляются как смещения в тексте после удаления маркеров и разэкранирования.

**Метаданные и тела сносок.**
- Область заметок: определения вида `[^id]: <!--{json}-->` и тело — строки с отступом в 4 пробела (при чтении снимается до 4 пробелов у каждой строки, пустые строки сохраняются; завершающие пустые строки тела при записи отбрасываются).
- Порядок сносок в файле — по `start` по возрастанию, затем по `end` по убыванию, затем по `id`.
- Аннотация без привязки записывается только сноской, с `"orphan": true` и сохранённой `"quote"` в JSON-метаданных, без маркеров в тексте.
- Неизвестные ключи JSON-метаданных сохраняются.

**Пересекающиеся диапазоны.** В Markdown диапазоны обязаны вкладываться, поэтому пересекающиеся (не вложенные) делятся при записи:
- Алгоритм записи: аннотации сортируются по `(start, −end)`; проход со стеком открытых диапазонов; если новый диапазон `[s, e]` пересекает верхний `[S, E]` (`s < E < e`), он делится в точке `E`: первая часть `[s, E]` остаётся с исходным `id` и заметкой, остаток `[E, e]` становится отдельным сегментом с `id` вида `a7k2m9~2` (далее `~3`, …) и метаданными `"part_of": "a7k2m9"` без текста заметки.
- Правило чтения (изменено): сегменты с одинаковым `part_of` **всегда** склеиваются в один диапазон от начала первого до конца последнего. В v1.0 склеивание зависело от отсутствия «чужих границ» между сегментами, но чужая граница между ними — именно та причина, по которой диапазон делили; такая запись не восстанавливалась бы, и тест «JSON → MD → JSON» не проходил бы на пересечениях.
- Приложение предупреждает пользователя при сохранении в `.md`, если есть пересечения («N аннотаций будут записаны в нескольких частях»).

**Ограничения отображения в других просмотрщиках.** Чтение и запись приложением без потерь гарантируются независимо от Markdown-структуры. Но подсветка `==…==` в Obsidian корректно отображается только для диапазонов внутри одного абзаца (маркеры не пересекают абзацы, заголовки, ячейки таблиц, элементы списков), не начинающихся и не заканчивающихся пробелом, и не находящихся внутри блоков кода (там литералы показываются как есть, а экранирование `\=` видно). Для диапазонов, не удовлетворяющих этому, файл остаётся корректным для Annotator, а в Obsidian подсветка будет неполной. Если исходный `.md` содержал собственные сноски `[^…]`, `==…==` или front matter, они экранируются или вкладываются в текст и в Obsidian работать не будут.

**Правка вручную в другом редакторе.** Если файл редактировали вручную (добавили сноску без маркера или маркер без сноски), приложение показывает отчёт о проблемах: «сноска без фрагмента» превращается в аннотацию без привязки (`orphan`), «фрагмент без сноски» — в аннотацию с пустым телом. `[v1.1]` Неэкранированные `[^` вне маркера закрытия, непарные `==` и «лишние» закрывающие маркеры также попадают в отчёт; текст сохраняется как есть.

### 11.4. Конвертация JSON ↔ Markdown

- Конвертация без потерь для всех полей, кроме неизвестных полей `extra` (в Markdown они записываются в YAML front matter под ключом `extra:`) и для пересекающихся диапазонов — внешне они записываются в сегментах (см. 11.3), но при чтении склеиваются обратно, так что набор аннотаций эквивалентен. `[v1.1]` Эквивалентность: совпадают `id`, `type`, `range`, `body`, `tags`, `color`, `resolved`, `created`, `modified` и неизвестные поля; `quote` не сравнивается (пересчитывается), кроме аннотаций без привязки.
- Тест на круговую совместимость: JSON → MD → JSON даёт эквивалентный набор аннотаций; тесты лежат в `format/__tests__`. `[v1.1]` Покрытие: вложенные, совпадающие, смежные и пересекающиеся диапазоны; аннотации в начале и в конце текста; текст с `==`, `[^`, `<!--`, `\`, строкой `<!-- annotator:notes -->`; пустой и многоабзацный текст; перевод строки CRLF; кириллица, эмодзи (суррогатные пары UTF-16); аннотации без привязки; property-based тест экранирования и случайных наборов диапазонов (`fast-check`).
- Команда «Экспортировать как…» создаёт копию в другом формате, не переключая формат документа.
- `[v1.1]` Команда «Экспортировать чистый текст…» записывает текст без аннотаций (в выбранной кодировке и стиле перевода строки). Команда «Экспортировать аннотации списком…» — Markdown или CSV (цитата, заметка, тип, теги, позиция).

### 11.5. `[v1.1]` Связь с исходным файлом

В v1.0 исходный `.txt` и копия текста в `.annot.*` могли расходиться, а правила не описывали, что тогда происходит. Правила:

- **Какой файл открывается.** `X.txt` → если рядом есть `X.annot.*`, открывается аннотированный документ (значок на вкладке; команда «Открыть исходный файл» открывает `X.txt` только для чтения).
- **Расхождение.** Принцип «исходный файл не меняется» сохраняется: правки текста в аннотированном документе не попадают в `X.txt`. Статус-бар показывает «текст отличается от исходного», если SHA-256 нормализованного исходного файла не равен `textSha256`.
- **Команды.** «Применить текст к исходному файлу» — записывает чистый текст в `X.txt` (в его кодировке, с его стилем перевода строки, с копией `X.txt.bak`) после подтверждения. «Обновить из исходного файла» — читает `X.txt`, заменяет текст и заново привязывает аннотации по цитате (шаги 2–3 из 11.2) с отчётом; доступна только после подтверждения.
- **Внешнее изменение исходника** никаких автоматических действий не вызывает: только индикатор в статус-баре.
- **Обычный файл без аннотаций.** Ctrl+S сохраняет его в исходной кодировке; автосохранения нет (`files.autosavePlain: false`); защита — снимок восстановления (11.6).
- **Конфликт форматов.** Если рядом лежат `X.annot.json` и `X.annot.md`, при открытии `X.txt` показывается диалог «Какой файл открыть» (с датой изменения и числом аннотаций); выбор запоминается для этого файла до удаления одного из них.
- **Перемещение и переименование.** См. 5.2, 5.3. Если исходный файл исчез, документ работает самостоятельно (`source` — только справочное поле).

### 11.6. `[v1.1]` Запись, резервные копии, восстановление

- **Атомарная запись.** (1) сериализация; (2) запись во временный файл рядом с целевым, с именем `.~<имя>.<случайные 6 знаков>.tmp` (такие файлы скрыты в проводнике и игнорируются наблюдателем); (3) `fsync`; (4) `rename` поверх целевого. Для `EPERM`/`EBUSY`/`EACCES` на Windows (антивирус, синхронизация OneDrive/Dropbox, другой просмотрщик) — до 5 повторов с паузой 50–500 мс; если не удалось — сообщение пользователю, данные остаются в памяти и в снимке восстановления.
- **Резервная копия.** `X.annot.json.bak` (или `.annot.md.bak`) — копия предыдущей версии: создаётся перед первой записью в сеансе и далее не чаще, чем раз в `files.backupIntervalMin` (по умолчанию 10 минут). Копия — не `rename`, чтобы целевой файл всегда существовал. Запись `.bak` на каждое автосохранение для документа 5 МБ порождала бы лишний объём записи на диск.
- **Автосохранение.** Через `files.autosaveDelayMs` после последней правки, но не реже `files.autosaveMaxWaitMs` при непрерывном вводе. Ctrl+S сохраняет немедленно.
- **Снимки восстановления.** При наличии несохранённых изменений каждые 5 секунд (если содержимое изменилось) в `userData/recovery/<хэш пути>.json` записывается снимок: путь, текст, аннотации, время. Снимок удаляется после успешного сохранения и при закрытии вкладки с выбором «Не сохранять». При запуске найденные снимки предлагаются к восстановлению (по каждому — «Восстановить / Отбросить / Сравнить»). Для обычных файлов без автосохранения — основной механизм защиты.
- **Подавление собственных событий наблюдателя** — см. 5.2.
- **Один экземпляр приложения** (`app.requestSingleInstanceLock()`): повторный запуск с путём файла открывает файл в уже запущенном окне. Для портативной среды замок привязан к `userData` соответствующей среды.

`[v1.1]` Дополнения:

- **Основная цель — `dir`.** `portable` у electron-builder при каждом запуске распаковывает приложение во временную папку (`unpackDirName`, по умолчанию с UUID сборки в `%TEMP%`), что замедляет старт (требование «до 2 секунд» не гарантируется) и противоречит принципу «ничего не пишется в систему». `portable` — опциональная цель для передачи одним файлом.

Режим разработки по-прежнему определяется `ANNOTATOR_USERDATA` (2.2).
- **Сборка на Windows и символические ссылки.** В ряде версий electron-builder при распаковке `winCodeSign` на Windows возникает ошибка «Cannot create symbolic link» (требуется привилегия создания символических ссылок). Обходные пути из обсуждения проекта: включить «Режим разработчика» Windows, либо добавить пользователя в политику «Создание символических ссылок», либо заранее положить распакованный `winCodeSign` в кэш сборщика (`.cache\electron-builder\Cache\winCodeSign`). Решение выбирается на этапе 0 и записывается в `README` проекта.
- **Подпись.** Неподписанный `Annotator.exe` вызывает предупреждение SmartScreen; для личного использования допустимо, для распространения — нужна подпись.
- Иконки и версия: `resources\icon.ico`; в `package.json` — `productName`, `appId`.

12. Создать аннотации с пересечением `[0,10]` и `[5,15]` → сохранить как `.md` → предупреждение о сегментах → открыть заново → набор аннотаций тот же (диапазоны `[0,10]`, `[5,15]`).
13. Текст с `==`, `\==`, `[^1]`, `<!-- annotator:notes -->` и аннотацией на границе → цикл JSON → MD → JSON даёт идентичный текст и диапазоны.
14. В режиме F9 выделить текст поверх нескольких фрагментов и нажать Delete / Backspace / вставить текст → документ не меняется; Ctrl+C копирует только видимые фрагменты.

16. Автосохранение при открытом файле не вызывает запрос «Перезагрузить / Оставить». Изменение того же файла другой программой — вызывает.
17. Тест производительности: документ 5 МБ и 5 000 аннотаций — прокрутка текста и панели без заметных задержек, открытие < 1,5 с, ввод символа < 50 мс (метод — раздел 13).
18. Рядом лежат `X.txt`, `X.annot.json`, `X.annot.md` → при открытии `X.txt` диалог выбора; в дереве значок конфликта.
19. Переименовать `X.txt` → `Y.txt` → `X.annot.*` переименован в `Y.annot.*`, `source` обновлён. Удалить `Y.txt` → вопрос про файл аннотаций.
20. Изменить текст аннотированного документа → статус-бар показывает «отличается от исходного»; «Применить текст к исходному файлу» записывает `.bak` исходника.
21. Приложение 10 минут работает под монитором соединений → ни одного исходящего соединения.
22. Все встроенные темы проходят `check-contrast` (правила 1–6 из 10.1); тема с ошибкой в `userData/themes` отображается в списке с причиной и не мешает запуску.

## 17. Открытые вопросы и риски

- Возможность запросить список системных шрифтов в Electron нужно проверить на практике (см. 9.2, спайк S4).
- Эффект флага `disable-lcd-text` зависит от монитора и настроек ClearType: на части машин разница малозаметна. Нужен тест на реальном экране (S5).
- Подсветка и сглаживание ClearType конфликтуют, если на подложке текста применяются прозрачность или композитные слои — проверить при реализации подсветки (использовать фон на `mark`-элементе, не накладываемый слой).
- Сложные Markdown-маркеры внутри исходных `.md`-файлов могут давать неоднозначности с `==`; правила экранирования (11.3) нужно покрыть тестами. `[v1.1]` Правила переписаны, инвариант проверяется property-based тестом (S3).
- Выбор между «редактируемым» и «только чтение» текстом влияет на устойчивость привязок; при правке привязки обновляются через маппинг изменений CodeMirror, но внешние правки файла обрабатываются только восстановлением по цитате.
